# Competitive baseline — 2026-09-04

Baseline captured before any performance work, so later changes have something to be measured
against. Produced by `tests/CompetitiveBenchmarks`.

## Environment

```
BenchmarkDotNet v0.15.8
Intel(R) Xeon(R) @ 2.80GHz, 4 logical cores (shared cloud VM), 15 GB RAM
Linux, .NET SDK 10.0.400, X64 RyuJIT
MediatorLite       @ df36323 (v2.1.0 line)
Mediator           3.0.2   (martinothamar), default options => Singleton lifetime, Eager caching
MediatR            12.5.0
WarmupCount=5  IterationCount=15   (ColdStart: 3 / 10)
```

> **Read ratios, not absolutes.** This is a shared 4-vCPU cloud VM, so nanosecond values are not
> comparable with results from other machines and run-to-run noise is higher than on bare metal.
> Every conclusion below rests on comparisons *within a single run*, which are sound.

`DirectCall` invokes the handler with no mediator at all. It is the floor: its 24 B is the
`Result` record the handler itself allocates, so **allocation above 24 B is framework overhead**.

---

## 1. Simple send — 1 request type per library, MediatorLite diagnostics OFF

`SmallProject`

| Method | Mean | Alloc | Overhead vs floor |
|---|---:|---:|---|
| `DirectCall` | 12.10 ns | 24 B | — |
| `MediatR_IMediator` | 153.16 ns | 224 B | +141.1 ns / +200 B |
| `MediatorLite_IMediator` | **50.02 ns** | **48 B** | **+37.9 ns / +24 B** |
| `Mediator_IMediator` | 23.94 ns | 24 B | +11.8 ns / **+0 B** |
| `Mediator_ConcreteClass` | 14.14 ns | 24 B | +2.0 ns / +0 B |

MediatorLite is 3.1x MediatR's overhead-free, but 3.2x Mediator's interface-typed overhead and
19x its monomorphized concrete-typed overhead. It is the only one of the three that allocates
per dispatch. The +24 B is exactly one empty object: the Transient handler instance.

`Mediator_ConcreteClass` has no MediatorLite equivalent — MediatorLite dispatches only through
`IMediator`. That row is a capability gap, not an unfair comparison.

## 2. Cold start — build container, resolve, first send

`SmallProject`

| Method | Mean | Alloc |
|---|---:|---:|
| `MediatR_ColdStart` | 118.755 us | 122.46 KB |
| `MediatorLite_ColdStart` | **5.129 us** | **6.85 KB** |
| `Mediator_ColdStart` | 13.449 us | 14.26 KB |

**MediatorLite wins decisively — 2.6x faster than Mediator and 23x faster than MediatR, at half
Mediator's allocation.** This is the direct consequence of *not* pre-building per-message wrapper
objects at container-build time, which is exactly what Mediator's `CachingMode.Eager` does.

Any fix modelled wholesale on Mediator's eager-singleton-wrapper design trades this away. It is a
constraint on the solution space, not a free win to copy.

## 3. Dispatch scaling — does position in the generated switch matter?

`LargeProject`, 66 request types per library. Verified against the emitted
`SourceGeneratedMediator.g.cs`: `MlScale00` is switch arm **#3**, `MlScale63` is arm **#66**.

| Method | Mean | Alloc |
|---|---:|---:|
| `MediatorLite_FirstOfN` (arm #3) | 84.82 ns | 48 B |
| `MediatorLite_LastOfN` (arm #66) | **133.88 ns** | 48 B |
| `Mediator_FirstOfN` | 38.74 ns | 24 B |
| `Mediator_LastOfN` | 43.90 ns | 24 B |

Two structurally identical requests, 63 switch arms apart, differ by **49.06 ns** — about
**0.78 ns per preceding request type**. Mediator's spread across the same distance is 5.16 ns.

**Dispatch is O(n) in the number of registered request types, not O(1).** README.md currently
claims "O(1) dispatch ... constant-time handler resolution" in two places.

Both libraries also degrade with project size independent of position — comparing the same
first-arm send at 1 vs 66 message types, MediatorLite goes 50.02 -> 86.19 ns (+36 ns) and
Mediator 23.94 -> 43.00 ns (+19 ns, where it crosses its 16-message threshold from an emitted
switch to a `FrozenDictionary`).

## 4. Pipeline behaviors — three no-op behaviors

`LargeProject`

| Method | Mean | Alloc |
|---|---:|---:|
| `MediatR_3Behaviors` | 438.24 ns | 752 B |
| `MediatorLite_3Behaviors` | **223.28 ns** | **320 B** |
| `Mediator_3Behaviors` | 46.42 ns | 24 B |

Going from 0 to 3 behaviors costs MediatorLite **+272 B, about 88-91 B per behavior** — one 24 B
Transient behavior instance plus one 64 B delegate, matching the emitted
`b1.HandleAsync(request, () => handler.HandleAsync(request, ct), ct)` exactly. Mediator adds
**0 B** for the same three behaviors, because it folds the chain into one cached delegate once at
container-build time rather than rebuilding it per request.

## 5. Notification fan-out — three handlers

`LargeProject`

| Method | Mean | Alloc |
|---|---:|---:|
| `MediatR_Publish3` | 396.08 ns | 592 B |
| `MediatorLite_Publish3` | **88.35 ns** | **72 B** |
| `Mediator_Publish3` | 17.72 ns | **0 B** |

MediatorLite's 72 B is exactly 3 x 24 B: one Transient instance per notification handler,
resolved on every publish. Mediator allocates nothing.

## 6. Scoped end-to-end — the realistic ASP.NET Core per-request shape

`LargeProject`. Create scope -> resolve `IMediator` -> send -> dispose.

| Method | Mean | Alloc |
|---|---:|---:|
| `MediatR_Scoped` | 307.6 ns | 456 B |
| `MediatorLite_Scoped` | **342.9 ns (ratio 1.12)** | 456 B |
| `Mediator_Scoped` | 212.0 ns | 224 B |

**MediatorLite measured slower than MediatR here**, with identical allocations. Scope creation
(~200 ns) is common to all three and largely cancels; the meaningful gap is the 131 ns to
Mediator, whose `IMediator` is a Singleton because its handlers are. MediatorLite's generated
mediator must be Scoped because it captures the resolving `IServiceProvider`.

Caveat: in a real ASP.NET Core app the scope is created by the framework and `IMediator` is
injected, so part of this cost is not attributable to the mediator. The MediatorLite-vs-Mediator

## 7. Default configuration — logging and tracing emitted

`DefaultDiagnostics`, 1 request type, no `[assembly: DisableMediatorLogging]` /
`DisableMediatorTracing`.

| Method | Mean | Alloc |
|---|---:|---:|
| `DirectHandlerCall` | 12.28 ns | 24 B |
| `Default_NullLogger` | 189.40 ns | 112 B |
| `Default_RealLoggerDebugFilteredOut` | **220.10 ns** | 112 B |
| `Default_Publish3_NullLogger` | 220.96 ns | 136 B |

Against the same send with diagnostics off (50.02 ns / 48 B), the **default configuration costs
+139 ns and +64 B with a null logger, and +170 ns with a real logger whose minimum level is
Information**.

The +64 B is two 32 B `object[1]` arrays — one per emitted
`__logger.LogDebug("...", "RequestName")` call. `LoggerExtensions.LogDebug(this ILogger, string,
params object?[])` materialises that array at the call site, *before* `ILogger.IsEnabled` is ever
consulted, so **raising the minimum log level does not remove the cost**. The generated code also
resolves `ILogger<IMediator>` from the container on every dispatch.

This matters because it is what a consumer gets out of the box, and because
`tests/MediatorLite.Benchmarks/AssemblyInfo.cs` carries both opt-out attributes — so the numbers
published in `docs/benchmarks.md` describe a configuration the documentation never tells the
reader to enable.
